# 项目驱动学习路线：先 Agent，再深入推理系统

> 更新：2026-09-22。依据你提供的学习思路整理，与《学习地图-大模型与Agent.md》的完整知识索引配套使用。
> 主方法：最小实现 → 暴露问题 → 学对应原理 → 改一个变量 → 验证 → 记录结论。
> 当前记录仍为 Bootcamp Week 5，周评估为空；“有 Python、神经网络基础”作为起步假设，不等于所有基础已通过考核。

## 如何使用

- 本文件回答“现在做什么、为什么学、做到什么程度”；知识地图回答“这个概念属于哪里、还关联哪些知识”。
- 每一层的模块编号从 1 开始。A0–A9、B0–B11 是项目阶段标签，方便对应原学习思路，不是全局章节编号。
- 优先跑通项目 A 的核心闭环，再进入 B；A 的高级功能可留待后续，不需要等它成为完整平台。
- Python、算法和基础面试练习少量并行；Transformer 从够用理解逐步深入，进入 B 前必须通过推理基础检查。
- 原 Bootcamp Week 1–5 文件保持原样；这里的“冲刺第几周”不代表正式 Bootcamp 周次，也不自动授予掌握等级。

## 对原学习思路的四点校准

1. 评测从 A1 开始留样例，A2 开始定量比较；A8 是完善体系，不是第一次评测。日志也从第一天记录。
2. Citation 元数据在解析文档时就保存，A3 再完成输出与核验。Rerank 是待验证的改进，不预设一定优于基线。
3. Workflow 是预设路径，动态 Agent 会根据结果选择下一步。用了 LangGraph 不自动等于做出了自主 Agent；项目可以合理混合两者。
4. 项目 B 的计时、负载、质量检查必须公平。显存更低、并发更高或换了引擎，都不自动意味着更快或更正确。

# 第一层：公共基础——只补启动项目所需的内容

## 1. A0：调用模型并理解输入输出

**要解决的问题：** 模型怎样生成回答？为什么会编造内容、输出被截断或超出上下文？

- **现在学：** Tokenizer、Token ID、输入/输出 token、Context Window、消息角色、System Prompt、自回归生成、logits 与采样、temperature、最大输出长度。
- **必须区分：** LLM 内部的 token embedding 是网络中的表示；用于 RAG 的文本 embedding 是检索模型产生的文本向量，二者用途和训练目标不相同。
- **动手：** 调用一个模型，固定问题，分别改变一项参数；保存输入、输出、token 用量、耗时和错误。若接口不支持某参数，记录限制。
- **过关：** 能画出“文本 → Token IDs → 模型 → 概率 → 采样 → 新 token”，说明模型参数不是可直接检索、实时更新的数据库。

## 2. 按需补 Python 和神经网络基础

| 何时需要 | 补哪些小知识点 | 验证方式 |
|---|---|---|
| A0 调 API | 函数、dict、JSON、HTTP、异常、配置与环境变量 | 处理空输入、错误返回和超时 |
| A1 做向量检索 | 向量、内积、范数、余弦相似度、矩阵 shape | 对几条文本手动比较检索排序 |
| A4 接工具 | 类型标注、Pydantic、JSON Schema、SQL 参数绑定 | 非法参数被拒绝，合法参数得到正确结果 |
| A5 管状态 | TypedDict/数据类、状态变换、分支、持久化 | 追踪一次运行经过的所有节点 |
| A6 做服务 | async、取消、连接池、FastAPI、测试和日志 | 并发请求互不串状态，超时能退出 |
| B0 看模型 | Tensor、广播、matmul、Module、eval、inference mode | 标注 Q/K/V、logits 的 shape |
| 后训练分支 | Autograd、链式法则、交叉熵、AdamW、训练/验证循环 | 解释 loss 和梯度，定位训练错误 |

已有基础可以用短任务验证后跳过重复讲解；无法解释的部分就地补强。

# 第二层：项目 A——从知识库问答到可靠 Agent

## 1. A1：最小 Vector RAG

**遇到的问题：** 模型不知道文档里的事实。

- **补原理：** 解析、chunk/overlap、检索 embedding、余弦相似度、向量索引、Top-k、上下文预算。
- **最小实现：** 选 3–5 份同领域公开文档；实现 load、chunk、embed、search、answer。简单向量索引或向量库选一个即可。
- **立即记录：** chunk_id、文档名、页码、正文、检索得分；建立 10 条可回答与不可回答的问题，打印实际召回片段。
- **过关：** 可以从回答回溯到输入片段；分清“解析缺失、召回失败、生成失败”。无依据时可以明确回答不知道。

## 2. A2：BM25 + Hybrid + RRF

**遇到的问题：** 型号、错误码和精确词检索不好，或同义表述漏召回。

- **补原理：** BM25 的词项匹配、中文分词、倒排索引；dense 检索的语义匹配；RRF 按排名融合，避免直接混合不同量纲的分数。
- **最小实现：** 对同一 query 同时检索 BM25 和向量库，按 chunk_id 去重，再融合排名。
- **验证：** 20 条人工核验问题，标注相关证据；比较 Vector-only、BM25-only、Hybrid。固定文档版本、切分和 k。
- **过关：** 展示哪些问题改善、哪些退化；Recall@k 是取回的相关项占全部已标注相关项的比例，Hit@k 是前 k 项是否至少命中一个，不能混写。

## 3. A3：引用与 Reranker

**遇到的问题：** 候选太多、答案缺少出处、引用看似存在却不支持结论。

- **补原理：** 两阶段检索、bi-encoder 与 cross-encoder、候选召回和精排的不同职责；chunk 元数据和证据支撑。
- **最小实现：** 从候选中选择少量证据，返回 answer、citations、source_chunks。引用 ID 由系统核验；不信任模型随意编造的页码。
- **验证：** 无 rerank 与有 rerank 对比检索指标、答案质量、延迟；把答案正确率和引用支撑率分开评分。
- **过关：** 能给出一个“答案正确但引用不支持”的反例；能解释 reranker 为何只处理候选。若收益不足，保留不启用的结果。

## 4. A4：原生 Tool Calling

**遇到的问题：** 文档不能提供实时库存，模型计算也可能不可靠。

- **补原理：** 工具名称、描述、输入 Schema、调用 ID、结果回填；模型提出调用，程序负责校验、执行和权限判断。
- **最小实现：** search_documents、calculator、get_product_info 三个工具，产品数据先存 SQLite。先用原生接口和清晰的 Python 调度函数，不急着加入框架。
- **验证：** 覆盖正确工具、错误工具、缺参数、非法参数、工具返回空结果；SQL 使用参数化查询，计算器不直接执行任意表达式代码。
- **过关：** 逐步讲清一次工具调用；区分“Schema 合法”“工具执行成功”和“业务结果正确”。

## 5. A5：State 与 LangGraph

**遇到的问题：** 分支、工具结果和恢复逻辑越来越难维护。

- **补原理：** State、Node、Edge、Conditional Edge、Checkpoint；Workflow 与 ReAct/动态循环的区别。
- **最小实现：** 把已跑通的工具流程迁移为图；保存 query、evidence、tool_results、answer、error、step_count。
- **验证：** 记录节点轨迹；给循环设置最大步数和停止条件；检查失败分支和不同会话的状态隔离。
- **过关：** 画出图并解释每条边的条件；说明哪些决策由代码固定，哪些由模型决定，以及为什么。

## 6. A6：故障恢复与人工确认

**遇到的问题：** API 超时、格式错误、重复写入、工具不可用。

- **补原理：** Timeout、有限重试、退避、Fallback、Circuit Breaker、幂等性、取消、checkpoint/interrupt。
- **最小实现：** 故障注入器主动返回超时/空值/坏 JSON；区分可重试和不可重试错误。仅在测试数据库实现一个配置写入工具，先生成提案再人工确认。
- **验证：** 请求必须有限时间结束；重试不会重复写入；拒绝确认时不执行；恢复时检查哪些节点可能重跑。
- **过关：** 展示一段“失败 → 定位 → 恢复”的轨迹，并解释重试上限与熔断器的区别。

## 7. A7：Memory 与上下文管理

**遇到的问题：** 多轮任务丢失状态，历史越来越长，不同用户信息混淆。

- **补原理：** 会话 state、历史摘要、长期偏好/事实、用户 namespace、检索、更新、过期、删除；Prompt 与 Context Engineering。
- **最小实现：** 当前任务保存在 thread state；长期只保存少量结构化信息，带来源和更新时间；为上下文设置预算。
- **验证：** 多轮继续、进程重启、用户隔离、偏好更新、删除记忆；检查摘要是否丢掉关键约束。
- **过关：** 说明什么不该保存、何时读写、如何纠正错误记忆。Memory 不等于无限追加聊天记录。

## 8. A8：完善 Evaluation 与 Observability

**遇到的问题：** 演示能用，却不知道整体成功率和失败分布。

- **补原理：** 数据划分、指标口径、人工 rubric、回归测试、消融；request_id、trace、span、版本记录。Evaluation 判断做得好不好，Observability 帮助解释实际发生了什么。
- **最小实现：** 将早期题集扩为 50–100 条，覆盖检索、计算、数据库、多轮、拒答和故障；开发集用于调参，留出集用于最终报告。
- **验证：** 分别记录 Recall@k/MRR、答案正确率、引用支撑率、工具选择/参数/执行成功率、端到端完成率，以及耗时和成本。模型裁判结果需人工抽查。
- **过关：** 一份有基线、失败分类、样本数和局限的报告；不把小样本成绩当成生产 SLA，不在留出集反复调参。

## 9. A9：MCP 与交付整理

**遇到的问题：** 同一个工具需要被不同客户端复用。

- **补原理：** Host、Client、Server；Tools、Resources、Prompts；工具发现、调用、Schema、错误返回、权限。MCP 是接口协议，不能替代业务权限和 Agent 决策。
- **最小实现：** 将一个已有只读工具封装成 MCP Server，客户端实际完成一次发现和调用；锁定所用 SDK 版本。
- **验证：** 无权限、错误参数、断连/超时；服务返回内容视作外部数据，不能覆盖应用自己的规则。
- **过关：** 能比较原生函数、普通 HTTP API 与 MCP 接入的代价；提供 README、演示、环境说明和失败案例。

## 10. 项目 A 的完成边界

两个月内的核心交付是：Hybrid RAG、可核验引用、三个工具、清晰状态流、有限失败恢复、基础会话记忆、评测报告。MCP 做一个小扩展；复杂长期记忆、GraphRAG、多 Agent、自动自我优化可后置。

- [ ] 从一个问题追踪到证据、工具、状态与最终回答。
- [ ] 有固定题集和至少一次有效对照实验，能接受改进无收益的结论。
- [ ] 能独立修改一处核心逻辑、补一个边界测试、定位一个错误。
- [ ] 能用 3 分钟讲清业务问题、本人贡献、实测结果和局限。

# 第三层：项目 B——从模型推理到服务性能

## 1. B0：Transformer 推理与模型加载

**问题：** model.generate 隐藏了什么？

- **学什么：** Q/K/V、缩放点积、causal mask、MHA/GQA、RoPE、Residual、Norm、MLP、decoder-only、logits；Tensor shape 与 dtype/device。
- **做什么：** 跑一个硬件支持的小模型，打印输入/输出 token 与实际长度，标出 forward 数据流。基础不足先在小 attention 模块验证因果性。
- **过关：** 能解释训练中已知目标序列可以并行处理，而普通自回归生成存在前后依赖。模型大小以可运行性决定。

## 2. B1：Generation Loop

- **问题：** 为什么输出越长，需要越多轮计算？
- **学什么：** 最后位置 logits、argmax/采样、EOS、最大步数、训练模式与推理模式的区别。
- **做什么：** 实现最小逐 token 循环；使用 eval 和 inference mode，在一致设置下与 generate 对照。
- **过关：** 能指出读取哪个位置的 logits，处理 EOS 和长度边界，解释循环中每次 forward 的输入。

## 3. B2：KV Cache

- **问题：** 哪些历史计算可以复用？为什么速度和显存产生取舍？
- **学什么：** 逐层 K/V、cache position、attention mask、序列增长；GQA 的 KV heads 与 query heads 不同。
- **做什么：** 比较缓存开启/关闭；查看实际缓存对象及 shape，不假设所有版本都采用同一种 past_key_values 结构。
- **过关：** 说明缓存后新 query 仍要读取历史 K/V。普通 dense Transformer 的缓存近似字节数为 2 × 层数 × batch × 长度 × KV头数 × head_dim × 每元素字节数，另外还存在框架开销。

## 4. B3：Prefill 与 Decode

- **问题：** 处理长输入与生成长输出，为什么性能表现不同？
- **学什么：** 矩阵乘法、FLOPs、带宽、算术强度、compute-bound 与 memory-bound。
- **做什么：** 分别计时 prompt forward 和后续增量 forward；改变输入长度、输出长度，记录硬件和 batch。
- **过关：** 解释小 batch decode 常受带宽限制，但不能把“prefill 永远计算受限、decode 永远带宽受限”当定律。API 首 token 延迟还含排队、网络等，不能直接等同纯 prefill 时间。

## 5. B4：单请求 Benchmark

- **问题：** 第一次很慢，测量结果不稳定。
- **学什么：** GPU 异步执行、同步计时/CUDA events、warm-up、重复测量、显存口径。
- **做什么：** 固定模型、revision、dtype、硬件、依赖、采样和输入；改变长度，存每次原始结果。内核计时与端到端客户端计时分开。
- **过关：** 说明 TTFT、总时延、实际输出 token 数、吞吐、峰值显存的定义；冷启动与稳态分开报告。不能把服务预留显存与张量峰值显存直接混比。

## 6. B5：并发与服务

- **问题：** 多个用户同时请求时，为什么尾延迟变差？
- **学什么：** 并发、队列、到达率、batch、背压、超时、吞吐与延迟；并发请求不等于实际 GPU batch size。
- **做什么：** 为 Transformers 基线搭一个明确标注调度策略的接口，逐步增加并发；测 req/s、输出 tokens/s、p50/p95 和失败率。若只串行服务，要明确其限制。
- **过关：** 区分排队和执行耗时；样本数足够支撑分位数，说明闭环固定并发与固定到达率负载的区别。

## 7. B6：引入 vLLM

- **问题：** 推理引擎在哪些负载下有收益？
- **学什么：** 在线模型服务、模型/硬件兼容性、引擎参数、标准接口、流式请求。
- **做什么：** 用相同客户端比较相同模型、dtype、tokenizer、输入集、采样、实际输出长度分布和硬件；逐步做多个并发点。
- **过关：** 对齐指标后再比较，不用 Transformers 的单请求离线耗时直接对比 vLLM 在线吞吐；串行基线的结果仅支持端到端方案比较，不能单独归因某个优化。

## 8. B7：Continuous Batching 与调度

- **问题：** 请求长短不同，为什么整批等待会浪费资源？
- **学什么：** Static batching、按迭代接纳/移除请求、waiting/running 状态、token budget、调度与缓存容量限制。
- **做什么：** 构造长短混合请求，记录吞吐、尾延迟、超时；画一个请求进入和退出 batch 的时间线。
- **过关：** 解释吞吐提升的机制、长请求影响及代价；不预设增加 batch 必然提高吞吐或改善每个请求延迟。

## 9. B8：PagedAttention 与缓存管理

- **问题：** 不知道输出长度时，怎样分配和回收 KV 显存？
- **学什么：** 逻辑/物理块、映射表、按需分配、内部/外部碎片；类比 OS 分页但分清两者不是同一机制。
- **做什么：** 画两个请求的逻辑 token 块到物理 KV 块映射；模拟增长与释放，先不读复杂 kernel。
- **过关：** 说明分页管理减少哪些浪费、块尾仍可能有内部碎片；它不同于 FlashAttention 的 IO 优化，也不同于跳过已缓存前缀计算的 Prefix Cache。

## 10. B9：KV Block Allocator 模拟器

- **问题：** 如何用可控实验理解分配、回收与碎片？
- **学什么：** free list、allocate/free、block table、容量不足处理和不变量。
- **做什么：** 先用 Python 模拟固定块分配与连续分配；对相同请求轨迹统计成功率、占用率、碎片、复用。First Fit/Best Fit 属于连续区间分配策略，不与“分页”混为同一层分类。
- **过关：** 覆盖重复释放、资源耗尽、回收后复用；所有物理块有明确归属。模拟结果只能解释内存管理，不能冒充 GPU 加速成绩。

## 11. B10：量化实验（可选）

- **问题：** 权重显存下降，为什么速度没有同比提高？
- **学什么：** FP16/BF16、INT8/INT4、scale/zero-point、权重/激活/KV 量化、反量化、量化 kernel、硬件支持；PTQ 与 QAT。
- **做什么：** 选一个实际支持的量化方法，固定任务与负载，比显存、TTFT/TPOT、吞吐及质量；记录加载格式和运行格式。
- **过关：** 报告精度/质量损失和运行限制；不把理论位宽节省直接当作整机显存或速度提升比例。

## 12. B11：Profiling（可选深入）

- **问题：** 已经知道慢多少，怎样找到慢在哪里？
- **学什么：** CPU overhead、GPU kernel time、数据搬运、同步、调度开销；基础监控与 profiler 的区别。
- **做什么：** 用 profiler 定位一段代表性负载，再选择一个优化验证。基础显存监控从 B0 即可做，不用等到最后。
- **过关：** 从轨迹提出瓶颈假设，并用对照验证；nvidia-smi 利用率不能单独证明瓶颈，采样分析自身也可能影响性能。

## 13. 项目 B 的完成边界与资源分支

- **必交：** 可解释的生成循环、缓存与阶段分析、可复现 Benchmark、至少一份有效对照、原始数据和局限。
- **有兼容 GPU：** Transformers + vLLM 同硬件比较；量化和 profiler 深入作为扩展。
- **暂无 GPU：** 先做小模型 CPU 推理、指标脚本、缓存理论和分配器模拟；GPU 性能对比明确标为待做。远程 API 无法让你控制底层缓存开关，不能据此声称验证引擎或 kernel 优化。
- **预算和时间不足：** 保证 A 的可面试质量，B 缩为机制验证和小实验。两个月内不强求量化、完整 allocator、kernel 优化全部完成。
